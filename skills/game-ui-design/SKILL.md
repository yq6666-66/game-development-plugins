# 游戏界面与交互设计

[English workflow](references/workflow.en.md)。输入是玩家任务、已有游戏状态、设备/输入、语言、布局约束和授权范围；输出是一屏或一条界面流程的设计契约、授权内实现以及真实操作证据。无需其他 Skill。

## 先定义玩家需要做什么

新项目：选择一条玩家决策及其最少信息，不凭习惯加入血条、背包或商店。已有项目：读状态来源和交互逻辑，区分信息缺失、显示错误与业务状态错误，不用新 HUD 掩盖玩法缺陷。保留视觉方向；纯方案任务只交付方案。

为每个必要元素写“信息来源→玩家判断→可用操作→结果反馈”。按行动紧迫性和使用频率安排层级，不把重要性等同于面积或发光强度。图标、文字、色彩与声音应表达一致信息；未知游戏数据不要生成假值当正式内容。

## 设计转换，而不只画静态屏幕

列实际适用的进入、正常、空、忙碌、错误、禁用、返回状态。每条转换定义输入拥有者、首焦点、取消语义、关闭后焦点去向以及业务副作用。菜单打开时游戏是否暂停由项目决定，但同一确认输入不应意外同时触发玩法。

动态列表变动、焦点项隐藏或删除时，设计有效后备焦点；不依赖引擎猜测。鼠标、触控、键盘与手柄只覆盖项目声明支持的方式，不能因支持一种就声称全设备可用。需要详细转换样例时读[界面契约](references/ui-contract.md)。

## 用约束实现布局

以容器、对齐、最小/最大范围和伸缩规则描述布局，检验长文、字号变化与支持的宽高比，而不是只按一张截图固定坐标。安全区与触控区域按目标设备验证，不照搬固定像素阈值。选现有引擎的布局/焦点机制；不强制 DOM、Canvas、某一 UI 框架或新的设计系统。

在可恢复副本中实现最小屏幕及真实状态绑定。明确哪些元素只读状态，哪些发出动作请求，成功或失败以业务结果驱动反馈；避免直接修改显示数字充当完成。

## 验证设计可操作

使用正常输入走进入→操作→返回，覆盖与本屏相关的取消、重复点击、焦点目标消失和失败反馈。比较相同状态、分辨率的前后画面；另测支持范围内的长文/窄屏，不用更有利机位掩盖问题。静帧只能证明布局观察，模拟尺寸不是实机输入验证。

交付状态/焦点表、改动、截图与操作记录，分别标记设计审阅、实现检查、宿主/引擎执行与设备覆盖。完整无障碍或可用性结论需要相应用户与设备证据；未做则保留未知。[来源取舍](references/sources.md)。
