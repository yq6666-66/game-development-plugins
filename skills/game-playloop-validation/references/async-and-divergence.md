# 异步检查与首次状态分歧

[English](async-and-divergence.en.md)。仅用于当前任务已有的异步流程或可复现状态缺陷，不要求引入 Godot、回放框架、遥测或新的游戏系统。

## 一、等待结束不是操作成功

输入：预期事件/条件、所属时钟、合理超时及取消约定。输出：操作结果、等待终止原因、后续状态与清理证据。

1. 分清等待的是渲染帧、物理步、事件还是条件。按当前实现选同步点，不以固定睡眠作为所有平台的标准，也不因机器慢就无限放大等待。
2. 注册观察后再触发可能同步完成的动作，避免事件先发生而观察者后到。等待必须可终止，超时、取消和成功分别记录。
3. 显式断言等待结果，再断言业务状态。某个函数返回、协程继续或测试进程退出，均不能替代成功条件。
4. 测正常完成及一个不完成/取消反例。重试前检查旧请求、回调和事件是否仍能生效，避免旧响应覆盖新一局。
5. 区分测试夹具的清理与产品自身的释放。先触发真实退出/重开路径并观察，再做夹具兜底回收；否则测试工具可能替产品清掉泄漏。对象数量、监听和资源分别按实际机制检查，不能用一种计数证明所有内存均已释放。

**Godot/GUT 来源细节，非跨引擎 API：**所读版本的 `wait_for_signal`、`wait_until` 返回是否在超时前满足条件；`assert_no_new_orphans` 只检查调用时的新孤立 Node。自动释放发生的阶段会影响断言，引用循环也不是孤立 Node 计数的完整覆盖范围。使用前匹配项目的 Godot/GUT 版本，不照搬示例的秒数或帧数。

## 二、先定位最早可见违规，再调查原因

输入：构建标识、初始状态、相关配置/随机状态、按序输入、预先定义的不变量。输出：首个违规事件、前后状态、候选写入链和未观察范围。

1. 先确认重现条件。确定性回放不可用时，保留多次观察的差异，不假造稳定事件序号；不要为了排错擅自重写成纯函数架构。
2. 只对最小重现记录相关事件，保留同一 tick 内顺序、稳定对象身份、读写前后值和不变量结果。最终分数或一张 HUD 截图不足以定位中间状态。
3. 默认顺序扫描找最早可观察违规。只有判定在序列上具有所需单调性，且检查点/回放忠实时，才考虑二分。状态可能违规后恢复，不能用普通二分跳过首次异常。
4. 沿实际依赖调查较早写入，区分“首次观察到错误”“可疑写入”“已验证因果”。序号 0 失败先核对初始化与输入契约，不能直接断言游戏无错。只凭最早写过某字段也不能认定根因。
5. 在隔离副本做单变量干预，检查原异常及相邻不变量。移除事件可能破坏原有前置条件，因此差异只是因果证据的一部分，不自动证明定位完成。

## 三、让已知坏样本检查测试是否真的有效

仅当测试评估在授权范围内，使用可恢复副本植入一个与真实机制有关的缺陷，例如漏掉一次去重或清理；不要修改发布构建。事先写清应失败的条件，分别运行健康基线和坏样本。

- 先区分评价测试检出能力还是评价 Agent 修复能力；二者不能互报成绩。
- 无效、不可达或在有限输入下没有行为差异的样本单列，后者不是数学意义上的已证等价。
- 评价 Agent 时隔离答案和参考差异，加入健康对照；共享仓库中换个目录不构成访问隔离。只有真正满足隔离条件才称盲测。
- 修复按行为判定，不要求与参考补丁逐字一致。修订方法后用新的保留样本，别把已见案例说成新证据。
- 结果只覆盖所选样本与条件；不得从一个坏样本通过推导全游戏无缺陷或某 Skill 普遍有效。
