# 云存档：分开验证持久化、同步与冲突

[English](cloud-save-evidence.en.md)

仅适用于已约定云存档的项目，排查断网、多设备或“已保存”提示。本参考不授权新增服务、账号或上传真实玩家数据；纯本地存档跳过。

## 输入与责任链

读取账号与槽位映射、存档键、同步触发点、版本/锁标记、冲突策略和获准隔离数据。追踪 `本地写入 → 远端提交 → 远端确认 → UI反馈`，分别记录本地持久化、待同步、远端已确认、冲突。发出请求不证明已接受，远端接受也不证明恢复后的关系正确。

## 最小检查

| 路径 | 需要观察的证据 |
| --- | --- |
| 断网后保存并重启 | 本地可恢复，不能显示云端成功；恢复网络后另核远端 |
| A、B读同一版本，A先提交，B用旧版本提交 | 根据已定策略拒绝、合并或明确覆盖，冲突可观察；未解决变化可恢复 |
| 远端确认 | 重读或第二客户端看到预期版本，UI状态匹配实际结果 |
| 账号/槽位切换 | 不把前账号的待同步内容写入新账号或另一槽位 |
| 用户关闭同步 | 本地成功与未同步正确区分，不误报失败或云端完成 |

这些是建议场景，未在本次研究执行。按项目风险选择，不要求所有产品具有多账号或手动冲突界面。覆盖须符合已批准策略，不自行改变存档规则。

## 容易出现的假通过

Unity Cloud Save 的写锁不匹配会拒绝更新；新建项不需要锁。已有项省略锁或传空锁可能绕过检查，因此移除锁后“写入成功”不等于冲突处理通过。不要把这种覆盖当通用重试。

客户端时间戳独自不能证明更新的因果先后，是本参考的工程推断，仍须结合实际版本协议验证。字段锁、文件同步、完整快照粒度不同；多字段一致性、删除传播、迁移、合并均需独立规则。不要强制供应商、重试次数、固定UI文案或合并算法。

## 来源、版本与范围

2026-11-15 阅读官方正文/API，无服务、引擎或游戏运行；仅原创总结和链接：

- Unity [write locks](https://docs.unity.com/en-us/cloud-save/concepts/write-locks)：概念全篇。在线版本，未确认发布日期。
- Unity [SaveItem / WriteLock](https://docs.unity3d.com/Packages/com.unity.services.cloudsave@3.4/api/Unity.Services.CloudSave.Models.SaveItem.html)：构造器与属性；页面标注包 3.4.2、生成日期 2026-10-13，生成日期不是发布日期。
- Valve [Steam Cloud](https://partner.steamgames.com/doc/features/cloud)：Overview、Notes/Best Practices、Save Paths、Cross-Platform、API与Auto-Cloud。默认会话前后同步与用户关闭选项不能推导成任意游戏的即时确认保证；设备专属配置不宜跟随玩家跨机器同步。Steam文件同步不是Unity字段写锁。
