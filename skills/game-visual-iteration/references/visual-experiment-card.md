# 视觉实验填写卡

[English](visual-experiment-card.en.md)

在候选版本冲突、参考不易转成行动，或静帧与操作反馈不一致时使用。按问题选填，不要求每轮做全部实验；这些表不授权改工程、安装工具或发布。以下例子是合成情境，未运行游戏。

## 1. 基线选择表

| 字段 | 填写内容 |
| --- | --- |
| 任务类型 | 既有项目优化 / 已授权的新样板 |
| 候选基线 | 版本或提交、入口、场景/画面、资产来源及可核实标识 |
| 实际证据 | 已打开或读取的内容、时间、环境；区分提供者陈述 |
| 差异与冲突 | 布局、交互、画面配置等哪些项不一致；不要静默拼接 |
| 本轮采用项 | 采用哪个基线、依据是什么；需用户决定的冲突标未决 |
| 不变项与回退 | 必须保留什么；原件/分支/备份及恢复方法 |
| 新样板假设 | 没有旧项目时记录获授权的可撤销假设，不凭空声称既有基线 |

示例：已有项目的构建 A 与编辑器场景 B 出口位置不同。本轮仅诊断主路径可读性，先确认目标版本；不能从 A 截前图、从 B 截后图。相反，获准从零设计的 2D 样板没有旧资产，可以建立标为实验基线的最小画面，不必因此阻塞。

## 2. 参考迁移表

| 参考方法与证据 | 本项目的问题 | 借什么 / 不借什么 | 实现前待核实 | 可观察改善与反证 |
| --- | --- | --- | --- | --- |
| 填来源与已读范围，不把宣传当实测 | 对象、距离或屏幕尺寸、运行状态 | 迁移关系与目的，不复制外观或玩法 | 当前工具版本、API、授权、输入输出 | 怎样知道有效；什么现象说明无效 |

合成示例：参考使用亮度层次突出目标。2D 解谜样板可以借背景与交互件的明度分离，不借参考的武器、金属配色或战斗界面。预期是角色移动时仍能识别交互件；若高亮遮住提示文字，则该方案没有通过。具体阈值由项目决定。

## 3. 静态与动态双证据卡

| 项目 | 计划 | 实际证据 / 结论 |
| --- | --- | --- |
| 假设与变量 | 玩家要更容易看清什么；本轮只改哪个可解释因素 | 记录实际参数差异，不以更换机位制造收益 |
| 固定条件 | 机位/视图、分辨率、质量、运行状态、其他相关条件 | 测曝光时曝光是变量，不同时锁死它 |
| 静态观察 | 有代表性的正常玩家视图、近/远或不同尺寸 | 对齐前后条件，记录未拍到或不适用项 |
| 正常输入路线 | 从哪里进入，操作什么，到哪里结束 | 实际步骤、目标/路径/HUD可读性及控制回归 |
| 动态代价 | 转向、运动、动画/效果遮挡；适用时测性能 | 设备与设置、实际数据、无预算时不宣称达标 |
| 判定与恢复 | 按项目约定保留、回退、继续或提交复核 | 每项 PASS / FAIL / BLOCKED / 未验证及依据 |

静帧改善而动态路线失败，不能整体判通过。程序化截图、编辑器预览、模拟设备与目标硬件分别记录；自动截图细则见[确定性与结果完整性](visual-regression-evidence.md)。不能以修复画面为由关闭玩法、输入或存档缺陷。

## 使用后检查

1. 是否只有本轮允许的变量变化，代价与反证是否一并保存？
2. 已有项目与新样板是否使用正确的基线规则？
3. 换成 2D、第三人称或其他类型时，是否仍能填写而不需要枪械、固定相机高度或坐标？
4. 证据是否真的来自所声明的运行方式？未执行的表格应仍是计划。
