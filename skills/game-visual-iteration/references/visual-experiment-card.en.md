# Visual experiment worksheet

[中文](visual-experiment-card.md)

Use when candidate versions conflict, a reference is hard to turn into an experiment, or stills disagree with play observations. Select relevant fields; this is not authority to edit projects, install tools or publish. Examples below are synthetic and have not been run.

## 1. Select the baseline

| Field | Record |
| --- | --- |
| Task mode | Existing project improvement / authorized new sample |
| Candidates | Version or commit, entry point, scene/view, asset source and verifiable identifiers |
| Observed evidence | What was read or opened, when and in which environment; separate provider claims |
| Conflicts | Differences in layout, interaction or effective rendering; do not silently mix versions |
| Selected basis | Which version and why; leave consequential unresolved choices explicit |
| Invariants and recovery | What must remain unchanged; originals/branch/backup and recovery method |
| New-sample assumptions | Authorized reversible assumptions when no previous project exists; not invented historical decisions |

Example: build A and editor scene B have different exit locations. A path-readability diagnosis must first identify its target version, not use A for the before image and B for the after image. An authorized new 2D sample may establish a labeled experimental baseline without old assets; their absence is not inherently a blocker.

## 2. Transfer the reference method

| Method and evidence | Project problem | Borrow / do not borrow | Verify before implementation | Observable benefit and counterevidence |
| --- | --- | --- | --- | --- |
| Source and read scope, not marketing as testing | Object, distance or screen size, runtime state | Relationships and purpose, not copied appearance or mechanics | Actual tool version, API, rights, inputs and outputs | What would support or reject the hypothesis |

Synthetic example: a reference separates targets through value contrast. A 2D puzzle sample may borrow separation between background and interactive pieces, not the reference's weapons, metallic palette or combat HUD. Moving players should still recognize the piece; a highlight hiding its text prompt rejects the change. Thresholds belong to the project.

## 3. Pair static and dynamic evidence

| Item | Plan | Actual evidence / finding |
| --- | --- | --- |
| Hypothesis and variable | What should become easier to read; one interpretable factor | Actual parameter difference, not a more flattering viewpoint |
| Controlled conditions | View, resolution, quality, runtime state and other relevant conditions | When testing exposure, exposure is the variable rather than a fixed condition |
| Static observations | Representative player views, near/far or different screen sizes | Matched before/after conditions, missing and inapplicable captures |
| Normal-input route | Where to enter, what to do, where to finish | Actual actions, target/path/HUD readability and control regression |
| Dynamic cost | Turning, motion, animation/effect occlusion; performance where relevant | Device, settings and measured data; no budget means no budget-compliance claim |
| Decision and recovery | Keep, revert, continue or review under the project agreement | Per-check PASS / FAIL / BLOCKED / unverified, with evidence |

A better still with a failed movement route is not an overall pass. Distinguish automated captures, editor previews, simulated devices and target hardware; see [visual regression evidence](visual-regression-evidence.en.md). Visual fixes do not close unrelated gameplay, input or save defects.

## Review the completed worksheet

1. Did only authorized variables change, and were cost and counterevidence preserved?
2. Were existing-project and new-sample baseline rules applied correctly?
3. Can a 2D, third-person or different genre use the fields without weapons, fixed camera heights or coordinates?
4. Does each result come from its claimed execution mode? Unexecuted worksheets remain plans.
