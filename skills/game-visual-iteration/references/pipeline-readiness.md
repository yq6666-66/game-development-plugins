# 首次绘制卡顿的证据边界

[English](pipeline-readiness.en.md)。用于已授权的画面性能诊断，不默认升级引擎、切渲染器或新增预热系统。

Godot contributors，[Reducing stutter from shader (pipeline) compilations](https://github.com/godotengine/godot-docs/blob/2a604b9307fca7b926431313f1b39718463fb2e7/tutorials/performance/pipeline_compilations.rst)，提交 2a604b9307fca7b926431313f1b39718463fb2e7，提交时间 2026-10-19，读取 2026-11-19。完整文本、图注与替代文字已读，未查看图像像素或运行引擎；开发快照不是目标稳定版本兼容承诺。

文档区分中间着色器代码与硬件/驱动相关管线；导出烘焙不替代管线预编译。所述预编译方案针对 Forward+/Mobile，不能照搬到 Compatibility/Web。资源预载也未必覆盖实例化后才确定的组合。监视器为累计创建计数，不是活跃管线数或帧时间。

## 原创诊断流程

1. 固定目标版本、后端、硬件/驱动、效果路径和画质；标缓存情况为已知冷、已知热或未知。不为测试擅自删除全局驱动缓存。
2. 用正常操作触发首次与再次出现，关联事件、帧时间和阶段计数增量。计数增加是线索，不单独证明卡顿因果；无增量也不能排除资源上传、脚本或其他瓶颈。
3. 仅对已识别的缺口比较现状与最小准备措施。若需隐藏实例，验证脚本、声音、碰撞、奖励和订阅没有副作用；提前执行一次玩法不是合法预热捷径。
4. 记录准备阶段时间/内存与首次使用峰值，不用平均 FPS 或开发机第二遍顺畅宣称解决。画质变化后重新核对相关组合，不预编译所有理论组合。

## 反例与验收设计（未执行）

比较预载但未接入场景的效果、已有实例的效果，以及实际支持的一个画质切换。按目标预算检查首帧峰值与交互正确性；准备时间/内存上升须显式列取舍。Compatibility/Web 项目必须走实际后端证据，不以无效烘焙开关当修复。若没有冷启动或目标设备，明确未覆盖，不能推断所有用户首玩无卡顿。
