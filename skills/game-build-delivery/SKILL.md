# 游戏构建与交付

中文优先；完整 [English workflow](references/workflow.en.md)。不绑定引擎、CI 服务或目标平台。输入是工程/构建约定、目标和允许操作；输出是可追溯产物、运行说明、日志与分层验证结果。

## 1. 建立构建身份

新项目选择一个获准目标和最小构建入口，不默认联网服务或注册账号。接手项目先读实际构建脚本、锁文件、项目版本、CI、导出配置及历史成功记录，复现原路径后再改。

记录源码提交和未提交改动、有效工具/引擎版本、依赖锁、目标架构、渲染/脚本后端、构建模式、入口场景和输出目录。只列会影响本次产物的项；“配置填了某版本”不等于执行真的用了它。无法确认关键版本时标明阻塞，不擅自升级。

## 2. 区分准备、构建和发布

阅读并确认脚本的实际副作用：本地输出、网络拉取、上传、签名、商店提交或部署。用户只要本地包时，禁用或不进入外部发布步骤；准备产物不自带发布权限。凭据使用已获准的存储和传递方式，报告中只记录所需凭据种类，不复制秘密或凭据文件进仓库/交付包。

需要平台 SDK、导出模板、许可证或不可访问设备时，明确缺项，继续不依赖它的检查。安装、付费和权限变化按宿主授权处理，不以编译任务推导额外授权。

## 3. 执行一个隔离样本

修改前保存可恢复基线。使用新的输出目录，避免将旧包误认为新产物；记录真实命令、工作目录、退出码和脱敏日志。先完成最小目标，不一次扩展全部平台矩阵。

构建失败按阶段区分获取依赖、导入、编译、打包、签名、上传；找到首个相关错误而不是只看末尾失败。重试应有依据和可控成本，不覆盖唯一成功包。缓存只用于加速：按影响输出的配置隔离，不把缓存保存失败当作游戏编译失败，也不把失败构建的残留当成功产物。缓存相关问题及具体引擎差异读 [构建检查与来源](references/build-checks.md)。

## 4. 核对产物，再在目标环境启动

按 [产物证据卡](references/artifact-card.md)记录文件、大小、哈希、构建身份和验证层次。确认产物类型满足目标：资源包、调试包、可安装包、网页目录并非互换。检查必需运行资源、许可证/署名、配置与启动入口，不把源码副本或缓存目录一起打包。

从交付副本启动，不依赖编辑器工作目录；执行约定的最短操作路径和正常退出。网页按项目规定的服务器/资源路径运行，不默认双击 HTML 即等于部署效果。无目标设备只能报告构建或启动的实际范围，不能由桌面通过推导移动端通过。

在需要可复现性判断时，用同一输入做隔离的重复构建或冷/热缓存对照。先确定所求是字节一致还是功能/配置一致；时间戳或签名差异需解释，不能把不同哈希直接判失败，也不能只凭都能启动判字节可复现。

运行时资源在编辑器存在、交付后丢失，或外部模型丢纹理时，按需读 [运行资源交付合同](references/runtime-resource-contract.md)，区分导入资源、原样文件和外部依赖。

## 5. 交接并保留回退

交付入口、输入、预期可见结果、失败提示、依赖、产物证据和未验证范围；保留上一可用产物及其身份。实际执行的源码检查、构建、包内容检查、启动、玩法、目标设备、发布各自报告 PASS/FAIL/BLOCKED/未验证。上传成功不等于部署可用，构建成功不等于完整游戏通过。发布或替换线上版本仍按当前任务授权，不自动继续。
