# Game build and delivery workflow

[中文](../SKILL.md) · [Checks and sources](build-checks.md) · [Artifact card](artifact-card.md)

Use for an authorized build/export/handoff task, not gameplay implementation or automatic release. Inputs are the real project, target and permission scope; outputs are traceable artifacts, launch instructions, logs and separate evidence levels.

1. **Identify the effective build.** New projects start with one approved target and minimal entry. Existing projects retain the current build route before changes. Inspect scripts, locks, engine/tool versions, CI and presets. Record source/dirty state, effective versions, relevant backend, architecture, mode, entry and destination. A declared setting is not proof it was used; do not upgrade to hide an unknown.
2. **Separate preparation from external actions.** Read script effects: local writes, downloads, uploads, signing, store submission or deployment. Local-only tasks do not authorize publishing. Use approved secret handling, never copy credentials into the repository, package or report. Missing SDKs, templates, licenses or devices block only their dependent steps; installs, costs and permissions follow current authorization.
3. **Run an isolated sample.** Preserve recovery state, use a new output directory, record command, cwd, exit status and redacted logs. Separate dependency, import, compile, packaging, signing and upload errors. Preserve the previous working artifact. Retry only with evidence and bounded cost. Cache identities must reflect output-affecting configuration; a failed optional cache save is distinct from a failed build, and stale outputs do not prove success.
4. **Inspect and launch the actual artifact.** Distinguish data packs, debug outputs, installable packages and web folders. Check runtime resources, notices, configuration and entry. Launch a delivery copy without relying on the editor directory, exercise the agreed shortest path and exit. Use the project's web serving requirements. If target hardware is unavailable, report the actual narrower evidence. Do not infer mobile results from desktop tests.
5. **State reproducibility and handoff precisely.** If needed, repeat the same inputs or compare cold/warm cache builds. Decide whether byte identity or functional/configuration identity is required; explain timestamps/signatures rather than treating every changed hash as failure. Record artifacts, hashes, inputs, expected observations, failure symptoms and recovery. Report source review, build, package inspection, launch, play, target-device and publication separately. Upload success is not a deployed smoke test. Preserve an earlier working package; release remains a separately scoped action.

When a packaged asset resolves to missing or fallback content, use the [runtime resource contract](runtime-resource-contract.md) to inspect imported representations and transitive dependencies.

No upstream scripts, runtime adapters or engine installations are provided. The referenced documents were read, not executed.
