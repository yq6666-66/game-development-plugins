# Select game tools and resources

This complete English workflow is equivalent to the Chinese entry. It contains no permanent “free” list and requires no other Skill. Use the local bilingual [evidence card](evidence-card.md).

## 1. Define the project gap

Identify the problem, target platforms, existing stack/versions, inputs/outputs, hardware, team skills, deadline, budget and intended use. For assets, distinguish in-game packaging, public source repositories, handing over raw files and standalone resale. For engines, separate editor host support from export targets.

Read existing agreements first. Ask only about consequential gaps; research other matters under explicitly labeled conditional assumptions. Compare no-new-tool and existing-tool options before suggesting a migration. Do not default new projects to any engine or web framework.

## 2. Check current official evidence

Select by fit, not stars, advertisements or search snippets. Open official documentation, release notes, platform support, pricing, licenses and relevant service terms. Record access date, version/plan, author/maintainer and inspected scope; pin commits when available. Community posts and Issues can expose risks but cannot grant license rights.

Check export restrictions, actual interfaces/dependencies, installation/services, maintenance, cost triggers/budget, commercial use, modification, attribution, packaging and redistribution. Free quotas, trials, open source, commercial permission and redistribution are distinct claims. Account for mandatory services, quotas, subscriptions/seats and build/distribution costs; label uncertain currency, region or taxes instead of inventing totals.

A root code license does not automatically cover dependencies, model weights, fonts, music, textures or generated outputs. Check each resource/version. Downloadability does not grant public-repository redistribution. If terms conflict or specific legal rights are uncertain, preserve the risk and seek rights-holder or professional clarification where needed; do not guarantee legality.

## 3. Preserve unknowns

For each claim distinguish official text inspected, author/community claim, your inference and actual execution. Inaccessible substantive content is not verified. Missing decision-critical pricing, licensing or compatibility blocks that candidate's adoption decision; mark it BLOCKED/unverified and continue independent research.

Explain the boundary: unknown redistribution rights can block public packaging without blocking a link-only note. No execution means no measured performance or project-compatibility pass. Record document and runtime status separately; historical snapshots do not prove current terms. Recheck changed versions, plans or intended use.

## 4. Recommend conditionally and plan a minimal check

Compare a few relevant candidates and a no-new-tool option. Explain inclusion/exclusion, costs, exit/rollback and alternatives. Let the problem determine count. If no single best option is supported, offer conditional routes rather than certainty.

Specify minimal verification inputs, environment, actions, observable result, failure signals and stopping conditions. If not executed, call it a plan. Record performance measurement conditions. A successful download, sample run or author video is not project validation.

## 5. Separate research from action

Read public materials under current research authorization without repeatedly asking permission for every document. Installation, accounts, uploads of project/personal data, generation services, payment, agreement acceptance, publishing and migration are separate actions governed by user instructions and host permissions. Recommendations and license text do not themselves authorize execution.

Deliver constraints, evidence cards, recommended/conditional/unverified decisions, minimal checks and unresolved matters. Do not add a static ranking or executable installer. See [sources](sources.md) for provenance and evidence limits.
