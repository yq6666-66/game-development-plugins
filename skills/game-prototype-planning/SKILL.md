# 游戏创意与最小原型规划

默认中文；需要英文时使用本目录内的 [English workflow](references/workflow.en.md)，它包含等价完整流程。无需安装其他 Skill。输出是**可检验的原型计划和决策依据**，不是已经可玩的游戏。

## 1. 先界定决定，而不是扩建功能清单

明确本次是创意探索、方案编写还是已获准实施中的规划阶段。制定计划不自动授权写游戏、启动引擎或发布。继承用户指定的平台、类型、引擎、规模与截止；未指定不默认选择浏览器或 Three.js。

新项目：从目标玩家、使用场景、期望体验和可用约束形成一个可撤销的小假设，不要求不存在的旧工程。多个想法只比较会影响下一步决定的差异。

已有项目：先读实际规则、入口和当前证据；区分已有决定与本次试验允许变更项。缺失规则先查记录，不能把自己的建议写成既有事实。重大未决取舍才提问；可逆细节可作为建议列明，不堵住整个规划。

## 2. 把体验翻译成规则与信号

写一个决定性问题，例如“玩家能否在行动前判断两种路径的代价”，而不是“是否足够好玩”。追踪 `规则 → 玩家选择/系统变化 → 可感知信号 → 预期体验`；标出未经证实的环节和竞争解释。

定义与问题有关的最少输入、可选行动、合法条件、状态变化、反馈和恢复方式。只在玩法需要时定义胜负、计分、资源或重开；开放式玩具也可以通过结束观察与复位构成测试，不强加输赢。规则数值由项目约定或明确标注的试验假设提供，不套固定时长、玩家数量或性能目标。

## 3. 选择能回答问题的最小载体

纸面、桌面角色扮演、交互草图、灰盒、可运行原型或现有项目中的隔离变体都可选。说明为何这个载体足够，以及不能证明什么。输入时序、物理或设备能力是问题时，纸面结果不足以证明运行行为；视觉、声音或叙事是被测机制时，不无条件全部删掉。

保留一个可回退基线；对照与变体只改变本次因素，列出控制条件。原型是可丢弃还是后续演化由项目需要决定，不默认单文件、不默认重写、不把演示代码直接晋升生产代码。列出必要任务、排除项、依赖与阻塞，范围与停止点按风险约定。

## 4. 预先约定怎样改变判断

在实施前写预期可观察信号、反证、竞争解释、采集方式及继续/调整/停止/证据不足的决策条件。把“规则正确”“玩家理解”“体验有效”分开；运行无报错不证明好玩，重玩或停留时间也不单独证明目标体验。

选择与问题相关的正常路径和反例；需要真实试玩时说明参与者、设备、输入及引导方式，考虑先后顺序与熟悉度影响。人数与阈值应与风险和条件相称，不能从教程复制。尚未试玩只给验证计划，不生成虚构反馈或保留/放弃结论。

## 5. 交付能被下一步使用的计划

用 [计划字段与例子](references/planning-sheet.md)按需整理：问题、事实/假设、规则、范围、载体、对照、观察与反证、决策条件、回退、未知与下一负责人。若包含实施命令，先核真实环境；不知道就列待确定，不编造可运行入口。

已有实验结果时先报告事实和覆盖，再判断继续、调整、停止或证据不足；通过只适用于被测假设，不证明完整产品。交接实现后，再用实际输入验证状态与反馈，不以本计划替代运行验收。来源取舍见 [来源与许可](references/sources.md)。
