## 1. 排查拖影，先分清哪一层在复用上一帧

**来源与观察。** AMD GPUOpen [FidelityFX Super Resolution 2.3.3](https://gpuopen.com/manuals/fidelityfx_sdk/techniques/super-resolution-temporal/) 的输入、反应遮罩、透明/合成遮罩、镜头跳切复位和历史累积相关段落，以及 [dispatch 结构](https://gpuopen.com/manuals/fidelityfx_sdk/reference_documentation/structs/ffx_fsr2_dispatch_description/) 对运动向量、遮罩和 reset 的字段说明，均北京时间 11-22 读取。在线文档标版本，未核页面发布日期或固定源码，未查看示意图像素、复跑样例或量测。两个页面是同一厂商文档，不算独立验证。

**机制。** 该时序重建用当前画面的深度和运动向量找历史数据，降低刚露出区域对旧帧的依赖；透明材质可能没有对应的深度或速度信息。该版本的反应遮罩改变当前与历史权重，透明/合成遮罩另影响像素历史保护，不能当同一旋钮。镜头跳切后的第一帧可通知清理历史；这不是每帧关闭历史。

**候选流程。** 已在范围内的时序渲染故障：先记录真实生效的渲染器、后端、质量档和叠层顺序，保持测试输入与镜头轨迹可比。对照连续镜头、遮挡物移开、透明元素、镜头硬切，先辨物体变换是否正确，再检查重建前后的目标区域与已有运动/深度调试证据。若项目已提供路径对照，以同内容且可比的原生或非时序输出做辅助，不拿不同细节级别直接比较。受控副本中只改一项候选，复验关键信息可读性和帧时间；局部处理可能把拖影换成闪烁或锯齿。若没有对应调试视图，记录未覆盖，不强加工具、SDK 或显卡。

**最小检验与成本。** 固定视角序列，比较正常移动、目标由遮挡变可见、硬切首帧到稳定期；若权威坐标正确而仅重建输出带旧轮廓，先查时序输入/历史而不改控制器；持续移动也要作为负向控制，防止用全局频繁清历史遮盖。未执行。对比显著增加捕获和设备成本，结果不外推到全部算法。映射视觉迭代的动态证据；不同于物理位置插值重置和 11-21 录制元数据同步，本项针对画面生成管线中的前帧样本。等实际项目证据再考虑进入参考。

## 2. 非核心 UI 期限：延长提示，不意外延长玩法或会话

**来源与观察。** Microsoft Game Dev / Xbox [XAG 116](https://learn.microsoft.com/en-us/xbox/accessibility/xbox-accessibility-guidelines/116)，页面更新 2026-11-13，11-22 读目标、范围、实施、例外和例图/视频说明文字；未检查画面或操作。它把非核心 UI 时间限制与比赛等核心玩法区分，也举共享实时多人倒计时的边界。对需要时间限制的 UI，文档讨论预先调整、预警及简单延长；重要非核心内容可提供手动推进。具体数字属于来源指南，不作为所有项目硬规则。

**候选流程。** 列每个限制的权威拥有者、到期影响、警告/确认、可调整条件、到期后恢复。分开三种时间：提示的**可见时长**、普通交互的**提交期限**、玩法/会话的**权威期限**。游戏已有规则允许时，可保留非核心教学直到主动确认，或提供回看；若任务安全性依赖既定超时，不擅自撤掉，真实期限到期后让提示显示已失效及可行恢复，不假装按钮仍可提交。不要为延长阅读将共享计时或认证会话私人延长。

**最小检验与成本。** 用延迟阅读、截止边界、恢复焦点、关闭UI后重入及共享倒计时做小组合；检查旧提示不会重新发送过期请求，支持的输入方式能完成允许的延长或返回。未执行。成本是通知/限时来源同步、可重入设计及设备覆盖。它补 11-20 的时钟身份与 11-21 播报通道之后的策略问题：拥有者、可变的期限及逾期后结果，不同于单纯换时钟或加声音。适合未来 UI 参考候选，不等于全无障碍合规。

## 3. 有路线也不等于到达：路径、避让、移动、目标结果要分开验

**来源与观察。** Godot contributors [Using NavigationAgents](https://github.com/godotengine/godot-docs/blob/2a604b9307fca7b926431313f1b39718463fb2e7/tutorials/navigation/navigation_using_navigationagents.rst)，固定开发快照 2a604b9307fca7b926431313f1b39718463fb2e7（2026-10-19）。读路径跟随与常见故障段、局部避让的机制和限制及相邻示例片段，不是全文/源码审计。Unity [SetDestination](https://docs.unity.com/en-us/engine/6000.0/script-reference/unityengine/ai/navmeshagent/setdestination) 和 [NavMeshPathStatus](https://docs.unity.com/en-us/engine/6000.0/script-reference/unityengine/ai/navmeshpathstatus)，版本 6000.0，读取请求/等待/结果和三种路径状态说明；未确认单页发布日期。均 11-22 读取，没运行样例或复现 GitHub Issue。Godot 文档许可文件前轮已核为 CC BY 3.0；Unity 页面不作代码复用许可依据。

**机制与推导。** Unity 对目的地调用返回成功指请求获受理，路线仍可能在计算且最终部分可达。Godot 文档的局部避让不负责修改路径，也不读取物理碰撞几何；地图同步前空路径还可能被判到路线末端。两者 API 不可互换，便携思路是把请求结果、候选路线、期望与实际位移、业务到达分别看。调试线、避让速度和路线结束信号不能单独触发任务完成。

**最小流程与验收。** 只在已有移动/寻路的授权任务中，记录请求目标/身份、当前路线状态、实际位移与业务允许的到达条件。过不了门时先区分不可达、绕行停滞、地图未就绪与真实碰撞，不默认每帧重寻路；只按任务约定反馈等待、替代路线、不可达或取消。测试一条正常路线、一个部分可达/启动尚未就绪的例子及临时障碍，确认无误发抵达反馈或奖励。还要测代表性窄道，不用零速度或物体重叠的极端样例替代玩家实际路径。已执行的仅是原创布尔/枚举断言反例，[具体见验证](../../validation/daily-2026-11-22.md)，未运行游戏引擎或 UI。成本是场景组合与层间可观测性；映射现有玩法「真实路线」门槛，准备证据分层，不新加寻路系统。
