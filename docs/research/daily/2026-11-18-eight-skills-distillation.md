# 八项游戏开发 Skill 逐项蒸馏 · 2026-11-18

[已先收藏的来源、固定提交与许可](2026-11-18-eight-skills-sources.md)

本篇是独立研究候选，不是已实施的插件功能。只读入口与必要许可/历史证据，以自己的话整理；没有安装、运行上游脚本、启动引擎、调用生成服务或进行用户试玩。下列最小检验是未来获授权后的验证设计，不是 PASS 结果。

## 逐项实践、边界与映射

### 1. higgsfield-websites：拆开游戏逻辑、表现和托管能力

- 可借鉴：在选生成服务前先列资产合同（用途、格式、尺寸、透明通道、风格、授权和替代件）；游戏规则、画面表现和服务端提供的房间/存储职责分开记录。
- 适用：确需平台托管的浏览器原型；平台 API、账户、费用与部署方式属于接入前提，不是通用引擎能力。
- 限制：不沿用自动登录安装、无需确认生成封面、不检查生成结果或自动发布的上游指令。服务许可不自动证明生成物可商用。
- 已有映射：game-resource-selection、game-visual-iteration、game-build-delivery 和 playloop 已覆盖相关门槛；不新增同名 Skill。
- 最小检验：用本地替代资产能否验证同一玩法？部署前是否已分开列出必要数据传输和公开内容？平台故障时是否能说明降级范围？

### 2. game-engine：把浏览器循环变成可观察边界

- 可借鉴：分离输入采样、固定或明确步长的更新与渲染；记录暂停、失焦、视口变化和恢复时的时间语义。
- 适用：Canvas/WebGL/JavaScript 网页游戏。名称不意味着包含 Unity/Unreal 原生底层实现。
- 限制：模板不能直接覆盖现有工程；帧率、物理引擎和网络方案按项目约定选，不默认引入全部依赖。
- 已有映射：game-engineering 和 game-playloop-validation 已吸收输入/更新/渲染、音频手势和 WebGL 恢复思路。
- 最小检验：同一输入轨迹在不同渲染帧率是否达到允许误差内的状态？后台恢复是否出现超大时间步、瞬移或重复监听？

### 3. game-developer：先定位瓶颈，再决定模式

- 可借鉴：先给目标设备和帧时间预算，分别测 CPU、GPU、内存和加载，再选对象池、缓存、LOD 或异步方案；状态进入和退出必须承担资源清理责任。
- 限制：不接受全平台一律 60 FPS、强制 ECS/LOD 或“任何 Update 分配都不可接受”这种脱离场景的绝对规则。示例未编译运行。
- 已有映射：game-engineering 与 playloop 已有配置/运行状态分离及先 Profile。新增价值是核对当前入口，而非重复计数。
- 最小检验：同一场景、设备和采样条件比较改动前后，既看性能也看状态恢复、内存增长和输入响应，防止优化破坏行为。

### 4. game-ui-design：验证操作链，不只看漂亮静帧

- 可借鉴：信息优先级和可操作区域先按任务排序；菜单进入、焦点迁移、返回和输入设备切换应有明确状态；色彩之外提供冗余信息。
- 限制：不把控制器优先、统一字号或安全区当所有项目默认；也不继承外部参考可覆盖用户要求的指令。原文角色履历不是本项目履历。
- 已有映射：已有同名 game-ui-design，以及 playloop 中焦点和 HUD 状态同步。本次入口提交与此前相同，不包装成新版本。
- 最小检验：用项目目标设备完成暂停→设置→返回→继续，并在切换输入设备、长文本和低视力模式下检查焦点和关键信息。

### 5. game-design-theory：理论只负责提出问题

- 可借鉴：把规则、玩家行为和体验分开；以资源来源/消耗、奖励时机、难度与能力关系整理设计假设。
- 限制：Bartle 分类不等于所有玩家的永久标签，固定响应时间和奖励曲线不等于“好玩”证据；不能把速查清单替代试玩。来源使用自定义许可，不复制其模板或正文。
- 已有映射：game-prototype-planning 已有更明确的可证伪假设流程，来源为另一个 akillness 同名 Skill。此次来源不同，不能误称同源重复；理论主题相近，不足以新增入口。
- 最小检验：选一个可撤销参数变化，列预期行为、竞争解释和推翻条件；记录少数玩家受到的阻碍，不能仅用平均时长证明满意。

### 6. game-feel：反馈有生命周期，也有可关闭版本

- 可借鉴：用游戏事件驱动音效、镜头、闪光和粒子；表现偏移与物理状态分离。效果必须能重入、叠加、终止和恢复，并提供减震/减闪/减动效选项。
- 限制：示例时长、强度和作者自报版本不是本项目验证；不得默认游戏有攻击或命中。时间缩放、实时时钟和暂停恢复要按具体引擎复核。
- 已有映射：game-playloop-validation 已有重叠触发和效果归零，不必新建 game-feel 入口。
- 最小检验：连续触发长短不一的反馈，在中途暂停、重开或销毁目标，检查相机与全局时间恢复。只用“最新触发 ID”消除旧回调，不自动证明最长暂停得到保留，需要明确选择延长、覆盖或合并策略。

### 7. multiplayer-game 历史版：从权威边界而非房间按钮开始

- 可借鉴：先分清谁验证输入、谁决定结果、谁能看见数据，再划分匹配与单局生命周期；重连先恢复快照再增量同步，避免客户端拿到本不应可见的状态。
- 适用：确有多人需求时，比较事件驱动与固定 tick 模拟。历史实现绑定 RivetKit，依赖与例子链接可能已变化。
- 限制：许可未明确，暂仅保存链接及独立概念研究，不移植代码。客户端主导移动加速度上限检查不是完整反作弊；示例 tick 率不是所有竞技游戏的生产建议。
- 候选映射：game-engineering 的架构边界、playloop 的状态恢复和 resource 的服务评估。独立多人 Skill 需先证明需求与足够验证覆盖。
- 最小检验：模拟双人同时入房、超时预留、重连、重复请求、越权实体修改与隐藏状态读取；分别记录安全性、一致性和体验，不只验证两窗口能连接。

### 8. develop-web-game 历史版：建立三种互相校验的证据

- 可借鉴：小步改动后，同时查看截图、结构化可见状态和控制台错误；提供受控时间推进接口，使测试可复现；完整走过开始、操作、胜负和重开。
- 限制：历史脚本不等于当前 Codex 官方可安装工具。不执行旧全局安装命令，不因示例有单画布或快捷键就改项目约定。时间钩子必须避免与真实循环双重推进。
- 已有映射：game-playloop-validation 和 game-build-delivery 已强调行为链与证据范围；本次补充准确历史与许可线索，而非立即引入脚本。
- 最小检验：同一测试输入产生可比状态，截图与状态文本一致；主动植入一个漏计分或重开残留问题，看测试是否真的检出。生成截图不等于已查看、无控制台错误不等于玩法正确。

## 优先级与去重决策

建议先巩固三条现有能力，而不是一次加入八个插件：
1. 工程边界：循环、状态所有权、输入与表现分离。
2. 反馈与 UI：正确操作链、可访问性、暂停/重开后的清理。
3. 验证闭环：截图、结构化状态、错误记录以及能检出错误的测试。

平台生成只在资产/托管需求明确时进入；多人只在项目确需时进入。现有七项正式 Skill 数量不变。上述优先级是基于当前仓库职责的研究判断，不是用户批准的实现计划。
