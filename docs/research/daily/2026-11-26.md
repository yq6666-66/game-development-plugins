## 1. 更新成功，不代表正在玩的旧页面拿到旧资源

**来源与范围。** Jake Archibald，[The service worker lifecycle](https://web.dev/articles/service-worker-lifecycle)，标示更新 2016-09-29，读 install、waiting、skipWaiting、手动与脚本更新段；非固定实现版本，未核浏览器实现。说明文明确警示：更新可让旧页面后续的请求经过新 worker。

**机制。** 对已经有离线缓存的网页游戏，页面脚本、当前控制器和实际响应可来自彼此不同的构建。复用同一资源 URL 时，新 worker 可能给还在跑的旧页面配上新资源；唯一版本 URL 则能避免同名覆盖，但若旧版内容已经回收，旧页面仍会请求失败。激活成功、资源命中和客户端版本一致是三道不同的检查，不规定所有产品都必须强刷或无限留旧缓存。

**最小检查。** 在隔离站点保留一页 A，完成一条可操作的正向路径；更新到 B 后保留原页，再触发首次延迟加载，同时用新打开的页面复核 B。记页面构建号、前后控制器版本、请求 URL、响应资源摘要和首个可执行操作。将「等旧页退出」和「接管旧页」作为明确不同的发布策略；只在项目已支持离线和热更新时检查断网、缺旧资产、更新失败与回退。成本是保留两代样本和测试切换矩阵；不更改实际发布策略。候选归构建交付，补现有产物验证的在途客户端，不重复 11-24 的引擎场景切换。

## 2. GPU 截图读回有行距，不能把缓冲区直接当像素

**来源与范围。** GPU for the Web Working Group [WebGPU 2026-05-21 候选推荐草案](https://www.w3.org/TR/2026/CRD-webgpu-20260521/#texel-copies)，读取线性布局与缓冲区复制校验；GPUWeb CTS contributors [固定提交 1d8c6b1f…](https://github.com/gpuweb/cts/blob/1d8c6b1faff9cdf6bc6365b278d013dede34dd5c/src/webgpu/api/validation/image_copy/buffer_related.spec.ts#L146-L220)，提交日期 2026-11-25，读取行距参数、单行例外与 WriteTexture 分支，未执行 CTS。

**机制。** 用 WebGPU 命令编码器把多行纹理拷入缓冲区时，必须提供合法行距，该行距须为 256 字节倍数，可能大于每行像素实际字节数。这不是屏幕宽度限制，也不套用到 `queue.writeTexture` 的 256 对齐规则。对单层未压缩 RGBA8 有效行长为 4×宽度。读回成功后仍可能是 CPU 打包误把填充当像素，而不是材质或渲染出错。

**最小检查。** 若已有 GPU 自制取证链，固定两个不同的已知行图案，选宽 63、64、65 各做两行，记格式、有效行长、行距、偏移、校验错误、解包后的像素摘要。64 恰好无填充，单测通过容易遮住错误；63、65 可检出错误的连续截取。先证明读回解包，再追查渲染；实际截图另核通道、色彩空间、坐标原点、分辨率与预乘契约，不用这项检查证明它们正确。对普通浏览器截图 API 不强加自制读回。成本是一个可控纹理及目标 GPU 测试，候选补画面迭代的截图证据链，与 11-25 材质透明模式不是同一层。

## 3. 音频恢复后能播放，不代表旧提示此刻仍有意义

**来源与范围。** W3C [Web Audio 1.1 2024-11-05 草案](https://www.w3.org/TR/2024/WD-webaudio-1.1-20241105/#AudioContext) 读 `currentTime`、`suspend/resume` 和调度节点；Chris Wilson [A tale of two clocks](https://web.dev/articles/audio-scheduling)，标示更新 2013-01-09，读时钟分离和预调度段。另核 WebKit [AudioContext.cpp 固定提交 ed04ff40…](https://chromium.googlesource.com/external/github.com/WebKit/webkit/+/ed04ff40674d30791da2d18b27b33ed805b50a82/Source/WebCore/Modules/webaudio/AudioContext.cpp#259) 的脚本暂停、恢复与中断分支；未运行该实现，不把一个提交代作 Safari 设备行为。

**机制。** `start(when)` 以音频上下文的时间为准；主动暂停上下文会冻结该时钟，但不自动冻结游戏状态。若在暂停前已经排了短提示，恢复后音频时钟到期时，新场景或新回合可能已经不再适用；若玩法也暂停、提示仍有效，又可能应继续提供。分开记录「规则事件发生」「排入音频时间线」「恢复时仍有效」与玩家实际听见。本文的有效性筛选是综合建议，不是规范内置机制。

**最小检查。** 在有暂停或音频恢复的项目中制作一条可预测提示，对照无暂停、两条时钟一起暂停、仅音频暂停而玩法继续；固定提示 ID，记规则状态、上下文状态、时钟、取消或重排和一次真实输出。对已分配的节点需检查是否可以阻止旧事件；需要续播的音乐与短时玩法提示不要套同一策略。不要为校准声音去重写游戏逻辑时钟，也不新增任意固定过期阈值。需用目标设备测用户手势、系统中断与听觉。补 11-24 并发声部主题的时间有效性，而非重复可听声部预算，归玩法/反馈参考候选。
