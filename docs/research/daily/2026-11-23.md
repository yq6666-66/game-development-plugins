## 1. 移动输出为零，不等于参与动作的控制都已释放

**来源与范围。** Unity Technologies Input System 1.20.1，标签解析到 a934411756c8862cb0f54da514a9b7cc1c000a2b（提交 2026-10-05）。11-23 读 [Vector2Composite.ReadValue](https://github.com/Unity-Technologies/InputSystem/blob/a934411756c8862cb0f54da514a9b7cc1c000a2b/Packages/com.unity.inputsystem/InputSystem/Runtime/Actions/Composites/Vector2Composite.cs#L120-L149) 和 [DpadControl.MakeDpadVector](https://github.com/Unity-Technologies/InputSystem/blob/a934411756c8862cb0f54da514a9b7cc1c000a2b/Packages/com.unity.inputsystem/InputSystem/Runtime/Controls/DpadControl.cs#L123-L141) 的数字分支、分量合成和归一化；未运行。Godot contributors [稳定版 Input.get_axis](https://docs.godotengine.org/en/stable/classes/class_input.html#class-input-method-get-axis)，11-23 读动作强度与按轴相减段；stable 链接会变，未锁定 Godot 版本。两者是不同实现例子，不证明所有设备或映射一致。

**问题与机制。** 两个相反的数字方向都按住，可以互相抵消得到零；同样的零也可表示两者都释放。Unity 的所读合成分支用方向是否按下构成两个分量，Godot 对该轴取两个动作强度的差。调试中还可能遇到死区、状态重置或读不到设备等情况，但不能仅凭相同数值诊断其原因。

**候选流程。** 只对明确采用「释放后才能重新移动」的已授权暂停或菜单流程，保留两个独立量：连续移动向量，以及当前玩家在本动作中的相关控制是否可靠地回到中立。数字方向查参与输入；模拟控制按项目约定用阈值/滞回识别中立，非机械意义上的物理松手。没有有效样本时显式标未知，由产品定义是否等回连、重采或明确取消；禁止把人工清零当真实证据。不要查全局任何键都未按，那会把无关确认键、第二玩家或辅助输入卷入门控；允许无缝继续移动的设计不应被强制改成释放门。

**最小证据。** 两方向同时按住→从暂停/菜单返回→只松其中一个，应该按已定释放策略处理，之后全部相关控制归中再新触发；加普通释放、无关键和无样本的对照。原创条件 fixture 已执行，不是 Unity/Godot 或真机验证。与 11-15 的「事件消费不等于轮询隔离」和 11-16 的重绑恢复不同，这里定位合成值丢掉方向身份；候选归玩法验证参考，成本是保留输入归属及设备矩阵。

## 2. 材质变体不完整时，每个 primitive 应回到自身基线

**来源与范围。** Khronos Group 及规范列明贡献者，[glTF 2.0 KHR_materials_variants](https://github.com/KhronosGroup/glTF/blob/70b5e4101725950fb8f3f94dd72c37e758ce5daf/extensions/2.0/Khronos/KHR_materials_variants/README.md) 固定提交 70b5e4101725950fb8f3f94dd72c37e758ce5daf（2023-08-28），11-23 读状态、设计目标、根变体、primitive 映射、回退和文字/结构示例，未渲染配图，未审引擎导入器或复现 Issue。规范文件标 Khronos 独立许可，不搬运示例。

**机制与推导。** 单一活动变体由查看器处理，每个 primitive 有独立映射。无活动变体或当前变体不在该 primitive 映射里时，合规查看器回到该 primitive 的普通 glTF 行为，而不是继承上一变体。规范目标是有限、预制的共享几何材质组合，不定义无限动态参数、游戏进度、外观权益或项目内长久身份。共享几何也不等于没有额外纹理、首用等待或内存成本。

**最小流程。** 已有 glTF 资产换色/外观切换故障时，先查导出与目标导入器的扩展支持和实际映射，再做最小两部件样本：A 改两个部件、B 只改其中一个，对照直接进 B、A→B 和撤到无变体。比较逐 primitive 的实际材质与局部画面，不以全局下拉框值或整个文件加载成功判绿。若产品支持多实例，切换一个并验证另一实例不串色。另记录实际构建与首用差异；不增加格式、导入器或付费资源。现阶段做了原创映射 fixture，未导出或渲染。关联视觉的资产到运行阶段门，比 11-16 的「交付资源加载」更具体，关注切换恢复而非文件出现。

## 3. HUD 看得见，不代表边缘手势能交给游戏

**来源与范围。** Android Developers [Views edge-to-edge](https://developer.android.com/develop/ui/views/layout/edge-to-edge)（2026-11-10 更新），11-23 阅读窗口重叠、栏/挖孔/系统手势三种 inset、横屏、沉浸模式与图注/示例片段，未测设备或观看演示；页面动态，无固定提交。该文档讨论的 Android 15+、target SDK 35+ edge-to-edge 条件只作对应平台示例，不直接套 Web/iOS 或引擎 UI。Android 提供的手势优先区不同于会遮住像素的系统栏与挖孔。

**候选流程。** 对获准的移动触控界面，分开记录实际渲染及系统遮挡、控件和手势起点/路径、当前窗口与坐标映射。背景可铺满不意味着关键交互可铺满。若边缘有系统优先手势，优先在游戏内移开手势起点或提供符合原设计的非边缘操作，保留系统返回与主页；不默认抢系统手势、写死边宽或给每层重复加 padding。旋转、系统栏回显、窗口改变或输入模型改变时检查可见与可操作两套结果。

**最小验证。** 同一场景走一次边缘和非边缘输入，观察游戏是否收到开始/取消、角色或 UI 状态是否清理、系统导航是否仍可用；目标支持两种导航模式时分开记录，模拟尺寸或静帧不代替真机输入。当前只做情境推演。成本是设备和姿态矩阵以及输入事件可观测性；在现有 UI Skill 的安全区建议上增加手势路由证据，不另外建技能。
