本次按公开版本动向与项目适配性选题，不做全网热度排名。近期明确信号：Blender 5.3（11 月 10 日）同时带来 EEVEE 材质灯光节点和原生高斯泼溅支持；SuperSplat Editor 3.0（9 月 9 日官方公告）改用 WebGPU；UE 5.8 官方将 MegaLights 标为 Production-Ready，同时引入 Lumen Lite，把新 Toon Shader 标为 Experimental。glTF 是长期互操作基线，不把它写成当月新技术。与[现有视觉技能](../../skills/game-visual-iteration/SKILL.md)及[资产阶段门](../../skills/game-visual-iteration/references/asset-runtime-gates.md)相比，本轮新增的是能区分失败原因的具体对照，不再重复一般性的导入、光照、LOD 清单。

## 1. 风格化材质：先决定什么要跨引擎保真

**案例。** Blender 里有清晰的卡通明暗分界，目标运行时却只剩一张平面色。把可搬的基础色、遮罩、法线等与受灯光实时驱动的效果分开。标准 glTF 材质不能直接携带任意 Blender 灯光节点图；功能需要时在目标端重建等价表现，或者经项目允许把不需要随灯变化的部分烘为贴图。保留原始材质，不先全局抬曝光。

**最小验证。** 用一物两视角，锁定曝光、环境、模型和构图。先保持光源固定核对导出材质及遮罩，再移动一盏灯：基础颜色在两个姿态都保留、明暗分界按预期移动才支持目标端重建通过。烘焙方案只对约定的静态效果验收，不把固定在表面上的阴影误认成动态受光。记录 PNG/GLB 等交付文件之外的目标引擎材质实例和质量档；单帧像也不能通过动态项。

来源：Blender Foundation 2026-11-10 [5.3 发布](https://www.blender.org/press/blender-5-3-release/)，读 EEVEE 与 splat 段；[glTF 导入导出手册](https://docs.blender.org/manual/en/latest/addons/import_export/scene_gltf2.html) 材质与可识别节点；Khronos [glTF 2.0 规范](https://registry.khronos.org/glTF/specs/2.0/glTF-2.0.html) 材质章节。以上验收方法是原创归纳，未运行 Blender 或目标引擎。

## 2. GLB 优化：给纹理和网格走两条独立对照

**案例。** GLB 变小，但低配端模型变白或首次显示更慢。保留 A 原件，B 只试纹理（KTX2/Basis Universal），C 只试网格路径（meshoptimizer，例如单独采用压缩；若另做简化，增加独立候选）。先检查声明的扩展、目标解码器及所需资源路径，再用目标加载器验证。KTX2 是容器；在这里讨论的是 Basis Universal 编码。无需升级资产工具链才能采用这个对照法。

**最小验证。** 选同时有基础色、细法线、粗糙度、切边透明和交互节点的原创建模夹具。保留同机位近看、远看及运动过渡的对照；glTF 金属/粗糙度图为 B/G，遮蔽读取 R，颜色与数据贴图分别核对。对 B 做一条缺少解码支持的反例：区分有普通图像备用源、扩展为必需、以及加载器能否明确报告失败；不要把某次浏览器自动降级当成 GLB 文件自带备用源。对 C 保留节点绑定、枢轴与动画，记录下载字节、首次可见时间、纹理内存及可见伪影，不能用压缩包大小替代另外三项。Khronos Validator 用于查结构；参考 Viewer 和实际游戏构建是另外两关。

来源：Khronos [KHR_texture_basisu](https://github.com/KhronosGroup/glTF/tree/main/extensions/2.0/Khronos/KHR_texture_basisu) 的 fallback、色彩和 mip 约束、[Validator](https://github.com/KhronosGroup/glTF-Validator)、[参考 Viewer](https://github.com/KhronosGroup/glTF-Sample-Viewer)；[glTF Transform CLI](https://gltf-transform.dev/cli) 和 [meshoptimizer](https://github.com/zeux/meshoptimizer) 的优化入口。未执行 CLI、校验器、解码器或加载器。

## 3. 实时渲染分档：拿同一条路线比较，不用宣传帧率定预算

**案例。** 高质量档截图好，但低档寻路时交互轮廓消失，或冷启动第一圈闪一下。先定不可退化的内容：关键入口、交互提示、角色剪影。围绕一个假设选一个变量，例如间接光质量或阴影距离；保持路线、曝光、分辨率、实际渲染后端和构建类型可比。若路线落到另一后端（如 WebGL 2），单列该后端的画面与数据，不与 WebGPU 混算。

**最小验证。** 记录高、低档实际生效配置；相同路线跑首次和预热后，分开采集相机运动中时间性闪烁、CPU/GPU 帧时间及 P95（支持时分别记 GPU 时间，不可得就标未测）。有可量化帧时间目标时，先写目标分辨率和设备再报告；只达到帧时但看不清交互项判失败。UE 用 Lumen Lite 或 MegaLights 作按需触发的官方例子，Godot 按 Forward+/Mobile/Compatibility 独立核目标；Three.js 按 WebGPU 与 WebGL 2 能力核查。不是在任意项目上开启这些选项的建议。

来源：Epic [UE 5.8 官方发布说明](https://www.unrealengine.com/news/unreal-engine-5-8-is-now-available) 的实时渲染段；[Godot 渲染器概览](https://docs.godotengine.org/en/stable/tutorials/rendering/renderers.html)；[Three.js WebGPURenderer 手册](https://threejs.org/manual/en/webgpurenderer)。未测引擎、GPU 或真机。

## 4. 高斯泼溅：先做远景实验，别让可见画面替代碰撞验收

**案例。** 摄影重建的建筑在预览器里逼真，进游戏却会穿墙，或者绕墙时出现排序伪影。第一轮建议拿它做静态环境背景，与可交互的网格、碰撞代理和导航分开。允许已有工具从 splat 生成代理，但要独立清理和核其坐标对齐、门洞及可通行区；近景交互失败或低端负担过高时，用简化网格或静态背景降级。拍摄素材、模型及发布授权另外核对。

**最小验证。** 同主视角截取网格代理与 splat 对照；绕行检查遮挡、透明排序、快速转向和细节加载；玩家路线包含可通行门洞与不可通行墙两条预期。检查首屏资源和实际目标端显存/帧时间，不用编辑器或观看端的成绩替代游戏构建。墙面看起来正确但玩家能穿过，碰撞仍失败。

来源：Blender [5.3 功能页](https://www.blender.org/download/releases/5-3/) 的 splat 导入和预览；PlayCanvas [SuperSplat 3.0 官方公告](https://blog.playcanvas.com/new-in-supersplat-editor-3-0-rebuilt-on-webgpu/) 及 [splat-transform 碰撞生成](https://developer.playcanvas.com/user-manual/splat-transform/collision/)。以作者文档为功能证据，未运行工具或演示。

## 落点与边界

优先整合第 1、2 项：一个解决 Blender 到引擎的画面变化，一个解决优化后仅在目标端出现的素材问题。第 3 项补目标设备渲染分档；第 4 项保留为实验路径。建议整合时放入已有 `game-visual-iteration` 的双语参考，不新设重复入口、不默认增加三方依赖。仅记录公开资料和原创诊断卡，不转存第三方截图、模型或脚本；代码许可、公开查看、二次分发和商用授权分别核。四项均为静态阅读和反例推演；没有工具、引擎、宿主、真机或实际游戏通过结论。

## English field cards

1. **Stylized material portability.** Separate portable texture inputs from a DCC-specific light response. Compare the same object under two light positions. A baked shadow that does not move can pass a static-look requirement, not a dynamic one. Rebuild the response in the target material only if needed.
2. **GLB optimization.** Use baseline, texture-only, and mesh-only variants. Test supported and unavailable decoders, and inspect the fallback declaration, semantics, animation and target screenshots. Measure transfer, first visible render and texture memory separately; validator and runtime evidence cover different questions.
3. **Real-time render tiers.** Define minimum interaction readability first. Keep the route and capture conditions comparable, record the actual backend, and report cold and warm frame times separately. A faster frame that hides an interaction target still fails.
4. **Gaussian splats.** Try static scenery first. Verify noise, occlusion, streaming and target cost from player input, and check collision/proxy alignment with an open doorway and a blocking wall. Promotional previews and generated collision are not playable-build evidence.
