## 4. 共同方法、冲突与实际落地

共同方法是：**声明 → 前置条件 → 权威观察点 → 正常/相关反例或中断 → 明确终态与未覆盖范围**。这不是统一引擎架构，也不是所有游戏都要有相同系统。

容易混淆的“矛盾”实际有条件差异：
- 截图冻结时间使像素更可比，但会削弱动态证据。保留受控截图与正常输入两条记录，不选其一宣称全通过。
- 取消/冲突可以是正确操作结果，也可能违背本次预期；不能将它们统一归为测试成功或失败。
- 菜单消费事件可以正确，而持续轮询仍会移动。先确定是否允许并行操作，再检查门控，不默认全停。
- 本地成功、远端冲突、UI 延迟可能同时出现。按确认的阶段报告，不能让一个绿灯覆盖其他失败。

4. 本周报、独立验证记录及 README 双语、CHANGELOG、PROVENANCE 更新。

## 5. 自主综合判断（非行业首创，非运行结论）

### 判断一：完成首先是证据闭环，而非动作执行完毕
- **依据**：上述截图终态、GUT 等待结果、云存档确认三类记录。
- **推理**：共同错误是在可见的中间环节停止追踪。为每个声明指定实际可观察的边界，比再增加一个笼统成功标志更有用。
- **适用范围**：已有异步、同步或构建验收任务；简单同步动作无需复杂状态机。
- **不确定性**：最终一致系统未必即时可观察，不能强制新增遥测或无限等待。只能如实声明已确认阶段。
- **最小验证**：用“请求发出未确认”“截图用例无结果”“等待超时后返回”三份合成记录检查报告是否拒绝整体 PASS，再在获准真实项目选一条检验。
- **插件影响**：本周用已有方法组成证据卡，尚无统计证据证明卡片降低缺陷率；此效益判断待验证。

### 判断二：越受控的测试，越应披露它替产品做了什么
- **依据**：冻结时序、隐藏 UI 的截图夹具与产品退出前的自动回收风险；现有视觉双证据卡。
- **推理**：控制变量提升重复性，也可能删除真正故障路径。因此受控证据与实际路径是互补关系，不能相互升级。
- **适用范围**：视觉回归、隔离测试、宿主发现等；纯逻辑函数测试无需强制玩家输入。
- **不确定性**：真实设备检查成本更高，覆盖范围应按风险选择，不以“都手动测”作为结论。
- **最小验证**：一份隐藏 HUD 的截图通过记录与一次正常输入 HUD 遮挡失败记录，应分别判定，不能相互抵消。
- **插件影响**：复用既有视觉实验卡，不重复新增规则；未来比较报告的遗漏率再决定强化哪些字段。

### 判断三：恢复的对象应包含上下文，而不仅是数值
- **依据**：存档身份/关系、菜单 held 状态、账号与槽位隔离。
- **推理**：数值正确却挂在错对象、旧意图继续生效、旧账号请求进入新槽位，都是上下文恢复失败。
- **适用范围**：实际存在的读档、场景/会话转换与输入中断；不强制对象图或统一服务框架。
- **不确定性**：单标量原型或非模态对话可能不需要额外状态机制；该归纳不是具体代码因果证明。
- **最小验证**：同显示名不同身份、关菜单后 held 残留、旧账号响应晚到三种合成情境，再选择实际项目支持的一项观察后续交互。
- **插件影响**：优先补路径例子，不新增近似 Skill；需要更多项目反例后再提升为通用决策规则。
